# Maestro Protocol

The user is the maestro. Codex and other agents act as the orquestrador.

## Ciclo de execução

O ciclo antigo — `Observe → Route → Select → Act → Verify → Report` — **foi subordinado**
ao ciclo Architecture-First pela emenda 2.4.0. Ele descreve hoje apenas a execução
posterior à decisão.

Ciclo vigente, em `contract/ARCHITECTURE_FIRST.md` §21:

```
Rehydrate → Understand Intent → Question → Confirm → Inspect Architecture
→ Identify Root Cause → Propose Alternatives → Draft ADR → Obtain Decision
→ Define Contracts → Plan → Acquire Lease → Engineer
→ Architecture Review → Engineering Review → Verify → Persist → Deliver
```

Regras que mudam a prática:

1. **Até `Obtain Decision`, tudo é somente leitura.** Ler, pesquisar, mapear, comparar,
   rodar teste não destrutivo, propor ADR — sim. Editar código, criar migration, alterar
   schema ou preparar commit de implementação — não.
2. **O lease só é adquirido depois da decisão.** O repositório não fica bloqueado
   enquanto a arquitetura está em discussão.
3. **Quando a mudança exige ADR, a ADR aprovada é o primeiro arquivo versionado.**
   Nenhum commit de código relacionado a precede.
4. **Revisão em duas etapas:** arquitetura antes de engenharia. Código excelente que
   viola a arquitetura é rejeitado.
5. Se durante a engenharia a decisão aprovada se mostrar insuficiente, a sessão entra em
   `ARCHITECTURE_REOPENED`, preserva o trabalho, **para**, e volta ao maestro. Nunca se
   ajusta a arquitetura silenciosamente no código.

Rotear por `SKILLS_ROUTER.json` continua valendo — mas depois de a decisão existir, não
como forma de escolher o que fazer.

## Discordância obrigatória

Quando a proposta do maestro produzir risco estrutural, discordar **antes** da
implementação, informando decisão entendida, risco, impacto de longo prazo,
alternativas, recomendação e consequência de manter a decisão original.

Depois disso a decisão continua sendo do maestro. O agente não contorna decisão aprovada
implementando outra arquitetura sob aparência equivalente.

A discordância é **única** (ADR-0011): apresentada uma vez, no formato acima; depois da
decisão o debate não reabre. Fato novo material reabre em **uma frase**, nunca em
investigação destinada a provar o ponto anterior.

**Modo incidente** (ADR-0011): havendo dano ativo — custo correndo, segredo exposto,
produção degradada — a ordem é fixa: conter → remediar → verificar contenção → só então
investigar causa. Atribuição de responsabilidade só em post-mortem *blameless* em
`DEV/EVIDENCE/`; frase defensiva durante o incidente é violação de contrato.

## Project DEV Context

When a project has a `DEV/` directory, use it as local project memory after reading the nearest project `AGENTS.md` and before selecting global skills. Start with `DEV/AGENTS.md`, `DEV/README.md`, `DEV/INDEX.md`, `DEV/HANDOFF.md`, `DEV/CONTEXT.md`, and `DEV/SPECS/ACTIVE.md`, then open only the files relevant to the task.

If `DEV/context/` exists (Compact Context Pack, generated by read-only collectors), read `DEV/context/_meta.json` first: when fresh (within `ttl_minutes` and `head_sha` matches `git rev-parse --short HEAD`), prefer `DEV/context/CONTEXT.md`, `INDEX.md`, and `WORKLOG-DIGEST.md` over re-deriving state (`git status`/`docker ps`/grep) or reading large files; when stale or missing, run the project refresh (e.g. `bash infra/rundeck/scripts/refresh_context_ccp.sh`) or fall back to live commands. Never hand-edit CCP files.

Create and update durable project documentation under `DEV/` by default. After substantive work, update `DEV/WORKLOG.md`, `DEV/VERIFY.md`, and `DEV/HANDOFF.md`.

Persistência é por **checkpoint** (ADR-0010), não só no fechamento: ao **abrir** change-set substantivo, gravar linha WIP no `HANDOFF.md` (`- WIP <título> — iniciado AAAA-MM-DD; estado: ...; retomar por: ...`); ao **bloquear** aguardando o maestro ou terceiro, persistir imediatamente o que falta e como retomar; ao **fechar**, ciclo completo removendo o WIP; **fim de sessão** substantiva nunca ocorre com `DEV/` defasado. Update `DEV/INDEX.md` and `DEV/CONTEXT.md` when the documentation map or project state changes, and update `DEV/SPECS/ACTIVE.md` when scope, acceptance, or status changes.

If the user or the project points to a private reference library outside the repo, read that pack's index first and only then open specific files. Do not treat a whole Drive export or PDF folder as automatic context.

## Token Discipline

- Prefer compact indexes over full catalogs.
- Avoid loading every skill directory.
- Avoid repeating long instructions across tools.
- Keep entrypoint files short and stable.
- Prefer `HANDOFF.md` and `SPECS/ACTIVE.md` over replaying long chat history.
- Keep `WORKLOG.md` short enough to be read in one pass.

## Global Changes

Changes to shared roots are allowed only when they improve compatibility or reduce duplication. Back up config files before editing.

Do not remove legacy roots unless the user explicitly asks.
